## From source endpoints to a prepared project

First retain two complete original V2 endpoint evidence groups. Each group
contains the six original byte inputs used by definition review preparation,
twelve independent candidate commitments, complete ordered physical contexts,
and the independently expected preparation CID. Original raw file hashes,
canonical record hashes, source identities, ASTs and role bindings remain
separate commitments. Construct the scoped registry, query and uniquely resolved
lookup through the existing resolver.

Call `prepare_definition_use_v2` with both endpoint groups, the exact alias
request and those original registry/query/lookup bytes and independent pins.
The request explicitly declares that a selected consumer body predicate is
biconditional with the donor head. It names every matching consumer body role
in original binding order. The result preserves both original definitions and
adds a separate alias AST, interpretation and `USES_DEFINITION` graph edge.
Its joint formula is:

```text
donor_definition ∧ (consumer_definition ∧ explicit_alias_assumption)
```

The alias is a caller declaration and remains unproved. A matching literal does
not establish predicate identity, governing applicability or statutory meaning.

Next call `prepare_definition_use_review_evidence_v2` with the exact component
file, independent component pins and the complete original use inputs. Build
its dependency manifest and call `build_definition_use_review_subject_v2` with
the independently retained ordered dependency closure. Finally use
`assess_definition_use_reviews_v2` with the subject, selected trust registry,
policy, reviews, original bytes, explicit evaluation time, observed dependency
pins and complete evidence bodies. Validation independently replays the whole
component and review assessment.

This review has its own fixed signing domain and combined scope. It covers both
original definitions, the explicit alias, full joint AST, source bindings,
contexts and dependencies. Endpoint reviews cannot approve this new subject.
Authentication checks declarations under selected keys; it does not establish
human identity, independence, expertise or the truth of the interpretation.
An unavailable trust registry and empty review population remain pending.

Then call `prepare_definition_use_corpus_v2` with the complete original
assessment file, its independent file hash, all seventeen original review
arguments and an exact versioned toolchain string. Its validator regenerates
the entire preparation. `write_definition_use_corpus_v2` and
`load_definition_use_corpus_v2` provide closed local transport with an
independently expected manifest hash and exact file readback.

A structurally valid pending or rejected assessment can produce engineering
text. The preparation retains its exact assessment status, blockers and
selected-trust prerequisite result. Every preparation remains
`build_eligible=false`, `preparation_only=true`,
`native_build_profile_registered=false`, `lean_compilation_status=not_run` and
`proof_status=pending`, even when synthetic credentials satisfy the selected
review prerequisites. No process or installed-toolchain probe runs through
these APIs.

## Supported endpoints and coverage

This profile requires two distinct physical source documents, one explicit
unary V2 definition per endpoint, matching `fol` or `tdfol` families and exactly
equal declared applicability. The original document scopes, release/edition,
source-version CIDs and complete symbol-table dependencies remain bound.
Unavailable, unresolved or ambiguous lookup refuses the candidate.

The first matching body role in original binding order supplies one
representative query. Every matching role and physical context is retained,
but `per_occurrence_lookup_verified=false`. Scope metadata and a representative
whole-predicate assumption do not establish governing lookup at every offset.
Same-document multiple definitions, several donors, cyclic components,
arbitrary normative uses and per-occurrence lookup require further profiles.

Complete source/use/review inputs share a 48-MiB preparation budget. Existing
per-input limits, one-MiB record bounds, 256 physical occurrences, 1,536 context
obligations, 512 body roles and authenticated-review limits remain in force.
The generated project is bounded to eight MiB and nine files. Complete
populations that exceed a bound refuse; evidence is not truncated.

The existing [sampled-source binding](legal_source_sampling_definition_binding_v2.md)
and [definition-only native build](legal_source_sampling_definition_lake_v2.md)
remain separate. They bind one actual unreviewed sampled definition and its
full pending source population; these new endpoint APIs do not consume that
sampling envelope. Keep the complete source population as a separately linked
replay dependency. Its FOL and TDFOL projections are two views of one physical
definition and cannot supply the two endpoints required here. An actual second
source and an explicitly supported donor/consumer interpretation are required
for source-grounded use qualification. Do not fabricate a second source identity
or reinterpret the existing opaque definition body to fit this profile.
