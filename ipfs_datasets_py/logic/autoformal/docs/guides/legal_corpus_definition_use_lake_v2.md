# V2 definition-use conditional Lean preparation

`logic.autoformal.legal_corpus_definition_use_lake_v2` prepares an exact local
Lean source project from a replayed
[combined V2 definition-use review](corpus_definition_use_review_v2.md).
Preparation, validation and transport execute no Lean process, installed
toolchain probe, model or build API.

The existing section-local definition/norm and shared-corpus preparations have
different input and AST profiles. V2 inputs retain their exact two-document
source identities, explicit alias assumption and new combined review scope.
They are not relabeled as a legacy norm. This adapter reuses existing native
fragment parsing/rendering and the closed local project transport.

## Original assessment and review inputs

```python
prepare_definition_use_corpus_v2(
    assessment_raw,
    *,
    expected_assessment_file_sha256,
    review_inputs,
    toolchain,
)

validate_definition_use_corpus_v2(
    preparation, assessment_raw, **validation_inputs
)
```

`assessment_raw` is the original complete UTF8 assessment file. Its independent
`expected_assessment_file_sha256` commits those exact bytes. The internal
review-engine `assessment_sha256` and full canonical assessment digest remain
separate manifest commitments.

`review_inputs` supplies all seventeen original named arguments to
`assess_definition_use_reviews_v2`: subject, trust registry, policy, reviews,
dependency manifest, component bytes/pins and original use inputs, the five
independent review hash pins, explicit evaluation time, observed artifact hashes,
observed dependency pins and original context evidence bytes. The native
preparer calls the existing assessment regeneration validator with that complete
population before rendering anything. It does not trust a saved authenticated
flag or synthesize credentials, reviews or observations.

The source groups retain both original HTML/acquisition/sampler/report/request
and candidate files, complete occurrence contexts and representative scoped
lookup. Existing validators preserve lowered limits and distinct raw/canonical
hash namespaces. Full source and review inputs remain separately retained
replay dependencies; this small generated project is not their archival copy.

A structurally valid **pending or rejected** review outcome may produce
candidate-only engineering text. Its exact evidence status, blockers and
selected-trust prerequisite result remain in the manifest. Altered assessment
bytes, resealed flags or a stale report inconsistent with the original replay
refuse. A newly replayed stale or rejected outcome cannot become qualified.
`build_eligible=false` in every case, including external-shaped synthetic
credentials whose selected-review prerequisites happen to pass.

## Native fragments and source custody

The exact donor, consumer, alias and full joint fragments are rechecked by
`legal_family_routes.prepare_native_fragment`. Original ASTs, formulas, emitted
Lean bodies, native symbols, source/version/scope records, role bindings and
all physical contexts remain bound. The same parameterized `Interpretation`,
Entity carrier and `Nat` evaluation time are shared by all fragments.

The manifest retains the original signed review dependency manifest **unchanged**.
Generated files and native rendering belong to a new downstream preparation;
they do not silently extend the signed review subject or its dependencies.
Review intake binding records the original assessment and component hashes,
subject/trust/policy/review/manifest pins, combined scope, evaluation time,
observation-map digests and evidence-body hashes.

## Project layout and conditional statements

The immutable `DefinitionUseCorpusPreparation` contains canonical
`manifest_json` plus exact sorted `(relative_path, UTF8_text)` file tuples.
There are nine generated files and six expected compiled modules:

- Pinned `lean-toolchain`, lowercase `legal` Lake target and
  `v2-input-bindings.json`;
- One parameterized `LegalCorpusV2.Prelude`;
- Separate content-named donor and consumer definition modules;
- An alias module importing both definitions;
- A joint module importing both definitions and the alias;
- Root `LegalCorpusV2` importing the joint module.

The fixed import graph is checked against the exact known, ordered module
population and is acyclic. Every complete generated byte is file-hashed.
Definitions expose their exact Boolean RHS as `bodyAt`; the alias exposes its
selected consumer predicate as `consumerPredicateAt`. The emitter uses each
AST's actual bound-variable name.

Three conditional statements are generated:

1. `consumer_predicate_iff_donor_body` assumes the exact donor definition and
   explicit alias. Their biconditionals compose to equate the selected consumer
   predicate with the donor's Boolean body for the supplied entity and time.
2. `joint_of_components` assumes the donor definition, consumer definition and
   alias, then assembles the original full joint conjunction.
3. `joint_matches_original` records the definitional equivalence between the
   modular conjunction and the original renderer's full joint formula.

These are generated proof obligations. The alias and original definitions are
premises, not asserted axioms or proved statutory facts. In particular, the
donor body and alias do **not** generally imply the consumer head: the consumer
body may include negation and unrelated predicates. No such consequence is
generated.

`#print axioms` commands and expected empty theorem-axiom dependency lists are
retained for a future actual native build. No output from those commands is
claimed here. `lean_compilation_status=not_run`, `proof_status=pending` and
`kernel_proofs_checked=false` remain explicit.

## Closed local transport

```python
write_definition_use_corpus_v2(
    preparation, directory, assessment_raw, **validation_inputs
)

load_definition_use_corpus_v2(
    directory, assessment_raw,
    *, expected_manifest_sha256, **validation_inputs
)
```

Writing requires complete independent regeneration and a fresh directory. The
existing transport exclusively creates the files, reads back their exact bytes,
then commits `corpus-manifest.json` last. Loading requires an independently
expected SHA256 of those manifest bytes and regenerates the entire preparation.
Missing, changed, extra, linked, nonregular or traversing entries refuse. An
incomplete directory is not a completed preparation, and no existing project is
overwritten.

## Finite bounds and source pins

All original source/use, review, observation/evidence and assessment inputs
share a 48-MiB native-preparation budget. Existing source sub-budgets remain in
force. Each ordinary JSON record/metadata population, including the complete
review list, retains the one-MiB/depth/node bounds. The existing authentication
engine's eight-MiB aggregate, 32-review and 256-evidence-body limits are not
raised. Not every population that fits a preceding profile fits this stricter
complete preparation. Overflow refuses as a whole.

Generated project files are bounded to eight MiB, nine files and the fixed six
modules; the separately sealed preparation manifest retains the common one-MiB,
depth and node bounds. Public import loads no renderer, compiler, signature
backend, build runner, incremental session or numerical model. Typed metadata,
raw hashes and complete budgets are checked before operation-owner imports.

The new wrapper, original review/use owners, native route's full producer
population, renderer and transport sources are pinned before/after preparation.
Absolute source-tree paths retain the existing portability boundary; these
checks do not authenticate a software distribution.

## Execution remains a separate gate

`toolchain` is an exact declared string such as `leanprover/lean4:v4.19.0`.
Preparation checks its versioned shape and binds the resulting file; it does not
claim that version is installed, current or authenticated. Installed binary and
library-closure checks belong to a future execution adapter.

The handoff retains expected modules, `.olean` paths, theorem names and the
bounded runner's future command recipe. Observed compiler binary pins and
theorem-axiom outputs remain absent; the V2 build-execution profile is not
registered. Existing legacy shared/incremental build APIs cannot accept this
new preparation by changing its schema label.

All source meaning/authenticity, actual human review, governing applicability,
per-occurrence lookup, formalization/admission, training/gold, backend/Lean
execution and proof authority flags remain false. Actual statutory decisions
and reviews, a compatible bounded V2 execution adapter with full native output
coverage, and any corpus/cache publication remain separate work.

### Parent bounds and closing input custody

The parent entry points first bound and detach one complete expanded caller
graph before any body hashing, full source replay or optional operation-owner
import. The graph contains exact assessment bytes/pin, complete original review
and endpoint inputs, time, dependency observations, evidence and toolchain. In
validation and writing it also contains the offered manifest text and all nine
offered file texts. Thus validation/writing can refuse a population whose
original inputs alone fit: the new combined graph still has the same **48 MiB**
hard ceiling. No existing input limit is raised.

The walker rejects cycles/custom objects/non-string keys, expands repeated
aliases rather than deduplicating their charge, and bounds depth to 48 and
nodes to 1,000,000. Scalars are plain null/boolean/signed64 integer/finite float/
UTF8 string, with designated immutable byte bodies accepted by subsequent
closed original-input checks. JSON scalar/punctuation byte accounting bounds
strings before encoding and charges raw bytes before descriptor replacement.
Existing endpoint, context, evidence and review sub-budgets also remain. The
project remains at most 8 MiB and exactly 9 generated files; the complete review
evidence map remains at most 256 entries. There is no truncation or partial
project acceptance.

`review_intake_binding.original_input_commitment_sha256` binds the full detached
original parent input graph, excluding the offered preparation. Its recipe is a
streamed typed tree. A dict emits `d<count>:` followed by sorted keys as strings
and their values; a list emits `l<count>:` followed by each child. Bytes,
UTF8 strings, decimal integers and finite JSON float texts emit tags `b`, `s`,
`i`, `r` respectively, followed by decimal body length, `:`, and exact body
bytes. Null/true/false emit `n`/`t`/`f`. SHA256 hashes the complete concatenated
stream. This distinguishes booleans/integers, bytes/JSON, ordering and all body
content without allocating a second expanded tagged tree or full serialized
commitment. It is an input identity, not an evidence or source-authenticity
claim.

Parent preparation, validation, loading and writing close by comparing the
actual caller graph, the detached graph and any offered preparation against
their opening snapshots. Mutable registry/policy/reviews, dependency maps,
evidence, time, parent limits and nested transport metadata are included.
An error is preserved if the closing comparison also fails, with a secondary
closing-failure note. The writer uses the original closed no-overwrite transport
and verifies complete parent regeneration during readback. The loader requires
the independent exact manifest SHA and every expected file byte, refusing extra,
missing, changed or linked members.

These are cooperative input-graph comparisons. The original parent/review
owners freshly replay descriptor-addressed physical source files during
validation, but this owner does not reopen every such file after rendering.
It makes no atomic filesystem-snapshot, operation-wide physical-file immutability
or arbitrary Python-reflection/monkeypatch attestation claim.

### Execution remains a separate gate

The parent preparation has `preparation_only=True`, compilation `not_run`, proof
`pending`, and `execution_handoff.status=parent_build_execution_adapter_not_registered`.
All parent semantic/authority/build flags remain false. Neither loading/writing
nor successful authentication executes a process, probes a toolchain or checks
a kernel theorem. The toolchain string must still be an exact version pin.

The existing `legal_corpus_definition_use_native_v2` validation/build APIs
continue to reject parent preparations. A separately reviewed extension must
explicitly regenerate the parent profile before/after bounded native execution,
pin binaries, preserve exact executed sources/modules/three axiom obligations
and distinguish conditional kernel observations from source/alias assumptions.
Do not relabel a parent manifest as official V2 or reuse a previous native
receipt. Definition sharing also requires a separate profile binding full
parent/physical/scope/edition/interpretation identity; equal text or formulas
alone do not authorize deduplication.

Qualification should combine the unchanged official Lake cases with a finite
parent cohort: complete FOL/TDFOL projects and TOML/import closure; genuine
parent signatures with explicit blocked/current trust outcomes; source/context/
lookup substitutions; forged assessments and resealed manifests/files;
whole-input overbounds before replay; caller/detached/offered mutation at
genuine rendering boundaries; exact closed no-overwrite transport; and refusal
through official/native entry points. Signed fixtures remain authored test
credentials and confer no real statutory or Lean authority. This addition
reports no new model, test or native execution result by itself.
