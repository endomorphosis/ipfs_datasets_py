# New source-bound native LegalIR inputs

The new opt-in cache and runtime accept independently pinned source occurrences
at384D or768D, with exact paragraph and literal double-newline clause vectors.
The old48-paragraph/216-vector assay and all selected checkpoint bytes remain
unchanged. The actual384D pilot admits all eight US Code spans and generates
16 complete canonical LegalIR candidates with the two frozen normative recipes.
This closes a bounded arbitrary-source input integration gap. It does not
measure statutory accuracy, train a decoder, or qualify logical/proof output.

## Implemented contract

`arbitrary_native_source_cache.plan_arbitrary_native_source_cache` requires
closed `{id, source_text, source}` requests. `source` is the existing SourceSpan
with artifactSHA/size, source_kind, release_id, document_id, language, citation,
half-open byte offsets and identity normalization. The resolver returns an exact
verified local path. Each selected span must equal its raw artifact byte slice.
Repeated text at different physical offsets remains separate; only identical
complete native EmbeddingInput identities may share encoder work. Literal
`\n\n` geometry supplies clause input boundaries without interpreting legal clauses.

The384D join checks current fixed GTE-small native receipt/profile, complete
actual token IDs/masks, raw float32 vectors, exact SourceSpan identity, hashes
and unit norm. The768D join accepts bounded complete recorded productions with
source text, tokens/masks, forward and complete model-loading inventory; bare
reports are refused. Recorded768 evidence lacks an embedded SourceSpan, so the
requested physical source is separately verified and this limitation is explicit.
Neither lane pads, truncates, projects a different width or supplies zero vectors
for missing inputs. Token overflow remains a refusal. Receipts establish recorded
consistency, without cryptographic execution attestation or legal meaning.

`dimension_source_inputs.produce_native768_sources(rows, *,
expected_source_rows_sha256, manifest_path, expected_manifest_sha256,
model_directory, code_directory, batch_size=1, max_seconds=600)` exposes the
existing complete CPU768 producer for selected source-only inputs. Supply at
most 64 ordered, unique closed `{id, source_text}` rows and 1 MiB total exact UTF8.
Each native input ID must be `source:` plus SHA256 of its exact UTF8 text. Pin
the complete ordered rows independently with `source_embeddings_768._digest`;
this is a canonical-value hash, distinct from a formatted JSON file hash.
Historical span IDs, separate physical occurrences and aliases stay in the
original source requests and are verified separately through the cache owner.
The producer assigns no train/validation split or historical occurrence.

The API delegates the unchanged complete-checkpoint CPU float32 eager,
right-padding, CLS/L2 path and bounded forward capture. It returns the existing
`fresh-bounded-native768-production/v1` envelope accepted by the cache, including
all source rows, complete token IDs/masks, vectors, actual forward observations,
complete 138-tensor loading inventory and complete/bare dense-path comparison.
Every selected source must pass the 512-token experiment gate before any forward;
no input is truncated. The original 8192-token producer identity remains distinct
from this stricter 512-token experiment bound. Caller-owned one CPU admission, one
Torch thread, a dedicated offline process, full source/runtime pins and a hard
process deadline are required; the API's at-most 600-second deadline is
cooperative. Batch size is explicitly 1..16. Physical-source authentication,
recorded execution consistency, model compatibility and legal qualification
remain separate.

Existing `bounded-native768-source-production/v1` receipts retain their exact
`bounded_owner` generation requirements. Adding this API changes that owner pin;
old reports and qualification generations remain historical and unchanged.
The fresh envelope remains its existing contract, with this wrapper/delegate
execution generation pinned independently by the caller. No old receipt is
repinned, and API availability alone supplies no new native result or legal,
training, decoder or Lean qualification.
