# Review evidence for native definition and norm candidates

`logic.autoformal.corpus_definition_review` supplies an explicit review subject
for the [native definition/norm candidate](legal_corpus_definition_norm_adapter.md).
It preserves the candidate's quantified definition biconditional, ordered
definition-and-norm AST, category guard outside O/P/F, bound variables and exact
graph/source records. These records use their own subject and signing domain;
they are never relabeled as canonical-rule or normative-scope graphs.

The adapter regenerates candidate, request, producer report, raw HTML and
extracted view under independently retained input hashes. Original raw file
hashes remain distinct from canonical content hashes and CIDs. The scope,
symbols, definition, norm, term, AST, input binding and original graph are
retained alongside every physical occurrence and ordered source role binding.

Every distinct physical source occurrence requires its own pinned context
packet. The packet is replayed through the existing statutory-context owner
against that exact occurrence's character/UTF8 geometry and separately supplied
dependency requests. A repeated literal at another offset remains another
occurrence. A definition block spanning paragraphs is not flattened into a
one-paragraph source selector.

Each context packet retains all six existing context obligations. The review
subject's slot inventory covers the complete occurrence population: thirteen
occurrences produce seventy-eight slots. The existing graph-review domain keeps
its original six-slot subject and thirty-two-obligation bound. The native profile
supports up to 256 occurrences and 1,536 obligations, subject to its complete
JSON and evidence byte bounds. Overflow refuses the whole input.

`prepare_definition_review_evidence` accepts the existing four original
`candidate_inputs` byte fields and exact `expected_candidate_pin`, plus ordered
`context_inputs` and independently retained `expected_context_population`.
Each context input names its source-occurrence CID, original packet bytes and
explicit dependency requests. Its population pin binds the occurrence CID and
raw packet SHA256. Preparations/subjects use the common one-MiB sealed-record
bound; aggregate original inputs and assessment evidence have an eight-MiB
bound. Complete large populations may exceed these limits before reaching the
nominal occurrence cap. Context summaries retain selectors, requests, all slots,
raw and canonical hashes; original full packets stay separately retained.

## Dependencies and authentication

The preparation includes deterministic artifact records and graph-to-dependency
edges for the exact candidate/request/report/raw/extracted inputs, companion
records, physical occurrences and context packets. Build their manifest through
the existing `legal_graph_dependencies` owner. Subject construction replays the
original preparation and independently pins the manifest and complete ordered
required dependency closure. Missing evidence stays visible; it cannot be
removed from the inventory to make a subject pass.

The native assessor regenerates its subject from those original inputs before
delegating to the existing graph-review authentication engine. Signature,
key/principal association, distinct legal/formal roles, authorized scope,
registry/policy/review validity windows, revocation, complete review population,
context evidence and current dependency checks share that engine. The original
graph review API, schemas and signing domain remain supported.

A native review requires its own claim, action and audience. A valid signature
from the old graph-review domain cannot be transferred. Reviewers sign the exact
subject and exact selected registry/policy generation. Changing source, scope,
AST, symbol binding, context population or a required dependency changes that
subject and reopens review. Unrelated artifacts outside its declared closure
remain independent.

Registry, policy, complete signed review population, evaluation time and current
artifact/pin observations are explicit caller inputs. There are no default
production keys, signers, reviewer identities, clocks or network lookups. Keep
the original candidate immutable and store the assessment as separately pinned
evidence. Validation regenerates the assessment from the same independent inputs.

`build_definition_review_subject` takes that preparation, dependency manifest,
all original preparation inputs, the independently expected manifest hash and
complete ordered `required_dependency_ids`. `assess_definition_reviews` takes
the subject, registry, policy, complete reviews and manifest, then requires those
same original inputs and independently retained subject/registry/policy/review
hashes, explicit evaluation time, current artifact/pin observations and exact
evidence bodies. `validate_definition_review_assessment` replays the result.
The native assessment carries the original input hashes, candidate/native
profile/family, preparation and companion CIDs, and explicit false authority flags.
The actual Profile G signature-owner source is pinned and preparation-owner
integrity is checked before and after verification; this does not authenticate
the installed cryptographic distribution or continuous filesystem custody.

## Meaning and admission

Authentication establishes that selected keys signed exact bytes under the
selected trust policy. It does not establish a person's legal competence,
identity or independence, statutory applicability, the truth of a declaration
or exhaustive governing context. Signed context dispositions remain reviewer
declarations, distinct from verified legal closure.

Synthetic Ed25519 fixtures test the complete authentication path. Fixture keys,
including fixtures shaped like an external policy, cannot supply production
review authority. Missing real reviews retain pending/blocking assessments.
The assessment always leaves source meaning, context closure, admission,
formalization, training qualification, accepted-view eligibility and proof
authority false. This adapter neither loads a model nor runs a native compiler.

The supported meaning profile remains the existing explicit section-local unary
`means` definition and unary norm. Broader definitions, legal sorts/arity,
cross-section applicability and selected lookup-to-native-symbol mappings need
their own reviewed profile. A lookup selection does not automatically create a
semantic `USES_DEFINITION` edge. A reviewed binding must explicitly name the
source occurrences, scoped native symbols, governing interpretation and review
evidence before a downstream graph or Lean corpus owner can admit it.
