# Source-bound entity preparation and resume

The v2 entity path binds preparation and resume to the exact entity and relationship inputs. It commits each physical source prefix with the corresponding queue changes, preserves local claim ownership, and streams resume snapshots through bounded Arrow batches and DuckDB staging. This is infrastructure for preparing knowledge-graph context. A prepared entity, a resume row, or a generated Lean source file is not an admit. Only the existing `lake build <Lib>` path can establish a Lean admit; the Constitution remains unformalized.

**Validation status: 132 guarded offline cases passed on 2026-09-27**, with zero failures, errors or skips. The successful r7 capture took 106.530 seconds including its 60-second stability window; pytest took 18.276 seconds. All 7,787 package files and 1,320 dependency files remained unchanged throughout this capture, including the eight execution-denied context paths. Exact selected-case membership, pinned logic paths, protected artifacts and resource-release checks passed. The measured source-sizing capture below concerns retained inputs and a legacy snapshot; full-source v2 ingestion, native checkpoint/model validation and real Hub traffic remain separate qualifications.

The implementation is in `ipfs_datasets_py/logic/autoformal/entity_cache.py` and `scripts/ops/legal_ir/ingest_ipfs_uscode_entities.py`. The focused core and caller suites contain 69 and 38 executed cases respectively. The remaining 25 cases exercise existing semantic and rendering contracts; the linked test receipt supplies exact membership and outcomes.

## What changed

A v2 binding contains the dataset and identity schema plus SHA256, byte count, and physical row count for both Parquet inputs. Paths do not identify source versions. A populated unbound cache, a changed input pair, or an old path-only counter cannot be adopted. Existing unmarked/v1 databases are checked through a read-only connection and refused before opening a writer. Column/nullability layout, the stored DDL identity, and the live primary-key constraint catalog must agree. There is no automatic migration of the live v1 cache or snapshot.

`enqueue_source_batch` requires the exact next physical ordinal. It validates at most 512 rows, checks immutable entity conflicts with a bounded Arrow relation and SQL join, and commits the insert plus cursor together. Exact duplicate input rows advance the physical cursor without duplicating logical entities. A guard failure rolls back both effects. Plain `enqueue` and path-only `save_checkpoint` cannot bypass a bound source cursor. Immutable entity identity includes the exact ID, type, label, properties JSON, dataset and schema; inputs are not truncated to fit.

The caller holds both source files open from initial full hashing through the operation. It checks current path/fd identity before each batch commit and fully rehashes at phase boundaries. This avoids rehashing both complete files for every 512-row batch while retaining fail-closed checks for changed or replaced inputs. These checks establish byte identity and local consistency, not authentication of the source publisher.

Containment requires the complete entity prefix and one complete relationship pass. It stages relationships and context updates in DuckDB. Exact repeated edges are harmless; conflicting `IN_TITLE` sources, `HAS_SECTION` sources, or `HAS_SECTION` targets are rejected before context changes. An unsealed preparation cannot replace inputs held by an active claim. The successful seal is tied to the input binding; repeating it checks current inputs and returns the original receipt while preserving later span and definition enrichment.

Bound claim/preparation methods require complete, sealed context. Completing a claim requires its original worker and token, and reports the actual matched count. Span, definition and reopen operations reject affected active claims and use transaction boundaries; malformed stored context is rejected instead of silently becoming an empty object. Definition closure includes every target reachable within two edges, with explicit bounds, rather than truncating the result to two targets. Proof metadata uses Boolean `False`. Task-board IDs use the complete SHA256 of the entity ID. A historical log collision involved an older literal CID-prefix recipe; the canonical code reviewed before this change already used a truncated SHA256 recipe.

Remote resume validation checks the full v2 snapshot: exact schema/binding, false authority flags, immutable entity records, canonical contexts, unique rows, entity/board correspondence, and agent/claim metadata consistency. Bounded Arrow batches are inserted into temporary SQL staging inside one transaction. Remote declarations never create local agents, adopt remote claim tokens, advance the local physical cursor, or complete an active local claim. Only a pending local row with the exact immutable record and already verified local context can accept a matching remote prepared observation. A final file check precedes commit.

Local snapshot export uses keyset pages, an explicit Arrow schema, one consistent owner transaction and one board refresh. It writes and validates a temporary Parquet file, fsyncs it, commits the database transaction, then publishes the snapshot. A failed commit leaves the previous complete snapshot intact. Cache/WAL overlap, aliases and a changing destination are refused. The ingestion CLI defaults to no poll and no upload, performs no implicit claim release, and uses a separate `autoformal/uscode/v2/<input-digest>/` Hub key and `entity-resume-checkpoint-v2.parquet` filename. The optional remote branch is not a claim that an upload or remote restore has been qualified.

The relationship census checked source-to-target multiplicity; the v2 validator additionally checks reverse `HAS_SECTION` ambiguity during preparation.

The new limits separate logical entities, physical input positions, total validation work and retained batches. The logical limits are 250,000 entities and 4,096 agents. The resume-row ceiling is derived as `2 * entities + agents + 1`, at most 504,097 rows. Each source file is bounded to 512 MiB and 2,000,000 physical rows, so duplicate source rows can produce a cursor larger than the logical entity count. The snapshot is bounded to 128 MiB compressed, 512 MiB aggregate declared/observed decoded work, 32 MiB per row group, 8 MiB per observed Arrow/JSON batch, and 2 MiB per context. A 64-row iterator is not a claim of an 8 MiB process peak: Parquet decoding, conversion and DuckDB staging add work and storage. DuckDB uses one thread and a 256 MB memory setting; process and spill-storage limits still require resource admission.

The old 262,144-row proposal limit could not represent the measured legacy snapshot. Its 256 MiB aggregate decoded budget was also too close to the measured 260,196,113 JSON bytes to accommodate the new fields reliably. The replacement limits derive the physical row count from bounded logical populations and keep aggregate validation work separate from the streamed batch boundary. They do not import a v1 success claim into v2.

## Cost and remaining qualifications

The expected opportunity is fewer per-entity database round trips and less retained Python snapshot/context data. Incoming entities use one bounded Arrow staging relation instead of a SELECT and insert operation for every entity. Containment uses bounded pages and a staged update. Resume validation uses temporary SQL tables rather than retaining all decoded entity, agent and board dictionaries. These mechanisms also add Arrow conversion, schema checking, full-byte verification, staging writes and snapshot readback. Their end-to-end benefit must be measured; no speedup, zero-copy behavior, GPU benefit or training-quality improvement is claimed here.

This work does not stream every semantic helper. Section/span/citation/inconsistency operations still retain their existing section-level Python collections, although their mutation and context checks are stricter. It does not prove federal-law completeness, qualify the separate 62,931-row source corpus as formalized, or integrate every graph entity into a training sample. Entity preparation stays separate from typed canonical compilation, shared legal-IR targets, sparse training updates, checkpoint quality and Lake admission. Temperature, context-window limits, the pinned workspace logic tree, and the prohibition on Mathlib or weight downloads are unchanged.

After the successful regression capture, the next useful qualification is a separately admitted full-source v2 run against the exact retained entity/relationship bytes, using a new cache and output directory. It should measure enqueue, containment, export, and reopened validation independently; record actual wall times, process/storage high-water marks and cache state; prove the complete physical cursor and row/board closure; and demonstrate interrupted-prefix restart, repeated sealed preparation, exact snapshot readback, and a self-observation import that preserves all prepared rows and local ownership. It must leave the existing span process, v1 cache, legacy snapshot, checkpoints and failed historical claims unchanged.

Hub qualification follows local qualification. A source-only immutable release plan should name every v2 file and digest, schema/input binding, declared dataset labels, and explicit false admit/formalization/authority fields. Offline dry-run and exact source-only download validation at a pinned commit should come before any real remote delivery claim. For a later live publication, record the parent and resulting commit, reverify downloaded source/checkpoint bytes and closure in a fresh isolated cache, and distinguish uploaded bytes from verified resumability. No model weights, native training, remote service listener or Lake admission is needed to establish that storage contract.
