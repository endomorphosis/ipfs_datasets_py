# Explicit idle CPU-pressure headroom

The administrative `expand_idle_cpu_pressure_headroom` API in `existing_resource_scheduler.py` changes only the stored CPU-stall cutoff of an existing idle scheduler. On October 17, 2026, the local cutoff was selected to increase from 50% to 65% under explicit user authorization, after source-binding qualification was repeatedly refused just above 50%. This allows admission at greater CPU pressure; it adds no CPU capacity or performance guarantee. Ordinary configuration defaults and the named local benchmark profile retain their existing limits.

Call with the exact existing policy SHA256 and an increased finite threshold no greater than 75. The default `apply=False` returns a plan. `apply=True` requires no leases, waiters, proof recovery or active backoff. Native telemetry must show known PID headroom, sufficient unchanged memory reserve, memory and I/O pressure below their unchanged limits, and CPU pressure below the proposed cutoff. Proof safety must remain enabled, and a named fixed profile cannot be changed through this API.

The operation uses the existing sibling scheduler lock and atomic compare-and-replace persistence. Only `config.proof_cpu_stall_percent` changes. Metrics, sequence, historical refusals, expired backoff, lane reservations and all other state remain intact. It neither prunes nor releases claims, initializes a new scheduler, resets history nor grants a workload lease. Old policy-bound clients refuse after application; new requests must explicitly bind the returned policy hash. Do not rewrite old requests or evidence to claim they used the successor policy. This guarantee applies to the explicit policy-bound facade. Legacy clients using `GlobalResourceScheduler(config)` can still reconfigure an idle scheduler and reset its history. Coordinate affected clients to use the successor policy; this operator does not change that legacy constructor behavior.

The campaign storage cap is a separate allocation described in [campaign storage allocation](campaign_storage_allocation.md). The distributed training request's 50 GB per-worker ceiling, physical free-space check and full outstanding-reservation accounting remain in force. Memory and I/O cutoffs, CPU-slot and process-slot capacities, per-attempt budgets and validation criteria are unchanged by the CPU transition. Workers still obtain and release normal native leases.
