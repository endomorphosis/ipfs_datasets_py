# Process-backend source review and proof-profile transition

The changed process backend is a separate source candidate. Its exception
cleanup changes preserve the existing public interfaces and leave integer
translation untouched, but they change the implementation identity attached to
conditional proof evidence. Retain the original release manifest and old proof
records. Qualify a new checker identity before admitting evidence generated by
this candidate.

The [inspection](../../../../../../artifacts/codebase-ir-backend-profile-transition-20261002/inspection.json)
retains exact source snapshots, three source diffs, AST comparisons, local Git
observations and both receipt-check reports. The
[transition contract](backend_profile_transition.json) specifies eight pending
acceptance gates. This is a source review and implementation handoff; runtime
tests, solver checks, database migration and Git integration remain pending.

## Keep source, proof and model identities distinct

The integer profile hashes the process source in its checker environment, and
the verifier hashes it again in the implementation profile supplied to the
property-cache binding. That binding derives both the canonical proof key and
the software-contract cache configuration/semantics identities. Consequently a
new backend belongs to a new exact proof namespace even when a source span and
its mathematical obligation are unchanged.

This edit alone does not require a new source CID, snapshot CID, contract CID
or compiled-IR CID. Those identities must still be independently rederived and
checked. Do not fabricate an equality claim by copying old declarations. Keep
old cache objects and proof-index rows under their original bindings; do not
rewrite their implementation hashes. Future lookup uses the candidate's
observed identity. Historical matches never substitute for current source
observation and fresh Z3/CVC5 execution.

For the proposed DuckDB/DuckLake index, append evidence rows keyed by exact
source/snapshot/contract/compilation, checker profile, environment and bounds.
Applicability queries select the qualified checker binding and current source
head. Older rows remain auditable history. Rechecking a row produces a new
attempt and result with lineage to the older row; it does not promote the older
row's authority. Solver errors, unavailable results, timeout, disagreement and
cancellation remain attempts, while only admitted terminal conditional results
enter the conditional-evidence index. Intent grounding must preserve that
scope and its assumption gate.

Each Legal, Security, Intent and Codebase inventory retains its independent
8D/384D/768D decoder, input profile, token/span budget, registry, index, lake and
Hub destination. A common process-owner change does not change an embedding
profile or justify retraining a decoder. Preserve cached vectors, decoder
weights and donor lineage. Model task qualification, independent held-out
evaluation, Legal text reconstruction and cross-width distillation remain
separate gates in the [release sequence](release_sequence.json). Autoencoder
outputs remain candidate formalizations until the appropriate native checks
and source bindings qualify them.

## Bounds and coverage still to resolve

Execution timeout starts inside the subprocess executor after validation and
workspace/input preparation. Cleanup performs several finite grace, drain and
join steps; their sum is not one end-to-end deadline. Sampling descendants and
RSS is weaker than kernel containment and can miss sufficiently short-lived
or escaped work. Output caps bound retained stdout/stderr and individual files;
pipe drain continues beyond the retained-byte cap, and workspace aggregate
size is checked after execution.

Exception cleanup discloses surviving pipe workers. The normal return path
joins readers with bounded waits, without an explicit failure for surviving
readers or a checked stdin-writer join. Existing startup tests cover reader
failure with `stdin=None`; candidate qualification needs writer-start failure,
blocked stdin, reader I/O failure and surviving-worker cases. These are
qualification gaps, not a finding that this stage reproduced a runtime defect.
BT02/BT03 require any needed owner changes and fresh receipts before acceptance.
