# Optional pandas imports explain the isolated conversion slowdown

The Docker SQL pair preserved every row but spent 40.269 seconds in native execute with VALUES and 38.692 seconds with column-list UNNEST. The corresponding host measurements were 3.399 and 0.946 seconds. The `_duckdb` extension SHA, one-thread setting and 512 MB memory setting match. Docker CPU throttling remained zero, and commit times were similar. Across six major fact families, the extra Docker time was roughly 41–44 microseconds per scalar value. These observations focus the investigation on conversion of Python values rather than statement count or commit overhead.

DuckDB's [v1.5.5 conversion code](https://github.com/duckdb/duckdb-python/blob/v1.5.5/src/duckdb_py/native/python_conversion.cpp#L386) checks the pandas missing-value objects before classifying each non-None builtin scalar. Its [optional import cache](https://github.com/duckdb/duckdb-python/blob/v1.5.5/src/duckdb_py/python_import_cache.cpp#L38) leaves a failed module import unresolved; [the importer](https://github.com/duckdb/duckdb-python/blob/v1.5.5/src/duckdb_py/importer.cpp#L8) can retry it on subsequent lookups. Host pandas metadata reports version 3.0.2. The retained Docker installation log includes NumPy 1.26.4 and no pandas installation. The deleted container's live pandas import availability was not directly recorded.

A mechanism-only control deliberately rejected pandas imports in a fresh process. Each 64-element integer or string list caused 130 attempts; 64 None values caused two. That control proves the repeated lookup mechanism, and its timings do not represent normal filesystem lookup cost.

The separate timing experiment used genuine dependency isolation with untouched standard import finders. Two private directories expose the same real DuckDB, NumPy, dateutil and six packages and metadata through symlinks. Only the available arm additionally exposes real pandas and its metadata. Fresh `python -I -S -B` processes use these directories, without installations, package removal, fake pandas objects or import hooks. Both arms have the exact `_duckdb` extension SHA `60ba180312ca4d6fcf14ebded76efcc1775485e69dcf89ec8f45653a5892a5ef`.

For the same 36,864 mixed scalar values across 16 queries, execute time was 0.02151 and 0.02168 seconds with pandas available, versus 0.99919 and 0.99578 seconds with pandas absent. Every returned value matched. Dependency import warmup was recorded separately. These two fresh-process pairs demonstrate a large causal effect of optional dependency availability in this isolated environment; they do not establish the exact Docker effect or a full-pipeline speedup. There is no timing threshold assertion.

`dependency-v2-*` contains the final raw results and command receipts. `dependency-links.json` records the package selection. `dependency_timing_probe.py` is the executed probe; `reproduce_dependency_pair.py` is a reproduction recipe assembled afterward, not an additional successful run. The initial run refused because isolated DuckDB distribution metadata was absent; its output is retained before symmetric metadata links were added. The synthetic fixture is permitted to publish; linked dependency package payloads and downloaded upstream source files must remain outside the evidence package. Upstream URLs and file digests are listed in `diagnosis.json`.

The minimal deployment fix should expose a real, compatible pinned pandas dependency with the existing NumPy version and verify conversion before runtime qualification. It must preserve source/CID checks, schema validation and transaction behavior. The column-list production patch remains unapplied. A fresh complete Docker qualification remains the gate for claiming the full 90-second Source384 path works.
